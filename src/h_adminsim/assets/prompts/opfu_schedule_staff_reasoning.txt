## How to read the schedule fields below (READ CAREFULLY):
Every ``schedule`` field is a per-date dictionary listing the time intervals that are **already OCCUPIED (booked)** on that date — NOT the available slots.
* ``"2025-06-13": []`` — the list is empty, meaning **no occupied intervals**, so the device/doctor is **FULLY AVAILABLE for the entire operating-hours window on that date**. Every minute of that day is bookable. An empty list is NOT a signal that the day is unavailable — it is the opposite.
* ``"2025-06-13": [[9.0, 10.25]]`` — occupied from 9:00 to 10:15; all other times within operating hours are available.
* ``"2025-06-13": [[10.5, 17.0]]`` — occupied from 10:30 to 17:00; all other times within operating hours are available.
* ``"2025-06-13": [[9.0, 19.0]]`` — the entire operating-hours window is one occupied block; the day is **fully booked**, no slot available.
* Only dates that appear as keys in the schedule are bookable. Never invent a date that is not listed.

## Test scheduling constraints (what makes a schedule valid):
A predicted test slot ``{{date, start, end}}`` on device ``D`` for test ``T`` is valid only if **all** of the following hold:
1. **Single placement.** Each required test appears at most once across the output list, on exactly one of its supporting devices listed under ``T.devices``.
2. **Operating hours.** ``start < end``, ``Start_hour <= start``, and ``end <= End_hour``.
3. **Later than current time.** The ISO timestamp built from ``date`` + ``start`` must be strictly later than ``Current time``. Past dates and earlier-on-today slots are invalid even if they are not occupied.
4. **Exact duration.** ``end - start`` (in the hospital's ``Time unit``) must equal ``T.duration_hour`` exactly. No rounding, no overrun, no shortening.
5. **Device availability.** The chosen ``[start, end]`` interval must not overlap with any occupied interval listed under ``D.schedule[date]`` for that date — not even by a single time unit.
6. **Priority is a hard time-order constraint.** For any two tests A and B with priority(A) < priority(B), A's end time must be at or before B's start time (using ISO timestamps so this holds across dates).
7. **Dependencies.** For every predecessor P listed in ``T.depends_on``, T's start ISO timestamp must be at or after ``P.end + P.result_hours`` (the moment P's result is ready).
8. **Avoid-same-day.** For every test ``X`` listed in ``T.avoid_same_day``, ``T.date`` must differ from ``X.date``.
9. **List ordering — non-decreasing priority.** The output list must be sorted so that priorities are non-decreasing along the list (i.e., item i's priority <= item i+1's priority).
10. **List ordering — global chronological.** The output list must also be sorted by ISO start timestamp, globally across all dates (i.e., item i's end ISO <= item i+1's start ISO). This is a strict, hard requirement enforced by the downstream validator.

## Partial scheduling is allowed (and expected when needed):
Schedule as many of the required tests as you can while satisfying every constraint above. If a particular test cannot be placed anywhere in the provided horizon (e.g., its only supporting devices are fully booked, or no slot satisfies its ``depends_on`` window), **omit that test entirely from the output list**. Do NOT invent a slot, do NOT shrink ``duration_hour``, do NOT use a date that is not in the schedule. Omitted tests will be re-scheduled by a later process. (An empty ``test_schedule`` list is acceptable only if no test at all could be placed.)


## Optimization based on the patient's preference:
* **ASAP**: minimize the latest ``end + result_hours`` across the placed tests (i.e., make the slowest result-ready time as early as possible). Multiple visit dates are acceptable.
* **Batch**: minimize the number of distinct visit dates first; among feasible groupings, prefer the one whose final ``end + result_hours`` is earliest.


## Step-by-step procedure (follow this when reasoning):
1. **Topologically order the tests.** Sort the required tests by ``priority`` ascending; within the same priority, place predecessors (anything listed in another test's ``depends_on``) before their dependents.
2. **Place each test in that order.** For the current test T:
   a. Walk through each supporting device ``D`` in ``T.devices``.
   b. Walk through D's listed dates in chronological order. Remember: a date with ``[]`` is fully free; treat any free interval of length ``T.duration_hour`` that fits within operating hours as a candidate.
   c. Reject any candidate slot that (i) starts at or before ``Current time``, (ii) overlaps an occupied interval, (iii) starts before any already-placed test of strictly lower priority ends, (iv) starts before ``predecessor.end + predecessor.result_hours`` for any predecessor in ``depends_on``, or (v) lands on a date that conflicts with ``avoid_same_day``.
   d. Among the remaining candidates, pick:
      * For **ASAP**: the earliest start ISO timestamp overall.
      * For **Batch**: a slot on a date already used by another placed test if such a slot exists and is valid; otherwise the earliest start ISO timestamp.
   e. If no candidate exists for T after scanning all devices and dates, OMIT T (do not place it).
3. **Sort the final list** by ISO start timestamp ascending. Because step 1 ordered by priority and step 2c forbids out-of-priority placements, this will automatically satisfy both ordering rules (#9, #10).


## Output format:
Respond with ONE JSON object containing only the key ``test_schedule``. Its value is a list. Each list item is an object with exactly one key (the **device code**, one of the keys under ``T.devices``); the value is ``{{"date", "start", "end"}}`` with ``start`` and ``end`` expressed in float hours.

Do NOT include ``fu_schedule``, ``test_visit_dates``, ``all_results_ready_at``, or any other top-level field. Do NOT wrap the JSON in commentary.
